# D-02　结构化输出守卫：schema 约束 vs 文本解析

对应书中：**第 3 章 3.2.3、3.8（模式卡「结构化输出守卫」）、3.9 节**。

## 一句话

同一批工单、同一个模型、跑 100 次，对比两条路径：**只做 `json.loads`** 与 **三层守卫（schema 约束 → 语义校验 → 带失败原因的有限重试 → 显式降级）**。看的不是绝对成功率，而是失败**落在哪一栏**：提示式路径的失败是静默的（`parse_error` 与 `semantic_error`，后者会带着合法外壳流进业务系统），守卫路径的失败全部落在 `degraded`（显式降级，可审计、可兜底）。

## 观察什么

1. **② 是"我们跑了二十个例子都没问题"的来源**：注入率为 0 时两条路径完全没有差别。任何可靠性结论都必须在有失败注入的条件下得出。
2. **③ 里提示式的失败与畸形率同量级上升**（0.10→0.30，`parse_error` 从 15 涨到 23），而守卫路径的 `ok` 不动，代价只体现在"平均调用倍数"上——**那 0.19 倍就是重试的钱与延迟**（第 3 章 3.2.2 的算式在这里变成可测的量）。
3. **④ 是本章最重要的一个观察**：加了两条业务规则之后，语法合法率一点没变（提示式的 `parse_error` 仍是 15），但语义失败从 11 涨到 85；守卫路径仍然全部拦住了，代价是**平均调用倍数从 1.19 涨到 2.22**、并有 22 次显式降级。这就是"约束解码不担保语义"与"重试不是免费的"两句话的可视化。
4. **⑤ 说明守卫的第三层可以部分补偿第一层的缺失**：模型只有提示式结构化输出时，守卫靠重试把 `ok` 从 74 拉到 96，代价是 1.34 倍调用。**但补偿有上限**——它换来的是成本与延迟，不是免费的能力，所以 4 章的路由仍然要优先选 `constrained` 的模型。
5. **失败落在哪一栏比失败多少更要紧**：提示式的 `semantic_error`（11 与 85 那两个数字）是**合法外壳包着错误内容**，它会一路流进业务系统；守卫的失败全部是 `degraded`，有原因串、可审计、可转人工。

模拟实现位于 `../llm.py` 的 `MockLLM._structured()`：它按能力画像的 `structured_output` 字段决定走约束式还是提示式，并注入三类真实世界常见的畸形输出（包解释、截断、单引号）。**注入率是旋钮，不是测量结果**——真实数字请用你自己的模型池与 schema 重跑，并把结果写进画像的 `structured_output` 字段（第 3 章表 3-2 的探针之一）。

## 常见问题

- **为什么两条路径各建一个 LLM 实例？** 避免随机序列互相污染，让两组数字可比。
- **真实调用时 `--malform-rate` 之类还生效吗？** 不生效，它们只作用于 `MockLLM`；真实路径的失败率由模型与你的 schema 决定。
- **`parse_error` 在守卫路径为什么是 0？** 因为画像里 `mock-flagship-1` 的 `structured_output` 是 `constrained`；想看非 0，用 `--force-mode prompted`（路径 ⑤）。
- **想接入 pydantic 怎么做？** 把 `validate_semantic()` 换成 `Model.model_validate(obj)` 即可，其余三层结构不变；本 demo 刻意用标准库实现，以保证零依赖可跑。

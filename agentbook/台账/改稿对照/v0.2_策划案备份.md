## 一、一句话定位

**面向架构师与技术决策者的 AI Agent 架构深潜书：框架无关、模式目录化、决策科学化——不讲"怎么搭一个 agent"，讲"为什么这样设计、怎么权衡、什么时候不该用"。**

电梯陈述：市面上教人"搭 agent"的书已经很多，教人"为 agent 系统做架构决策"的书几乎没有。本书把三年 agent 工程实践浓缩为一张五层参考架构总图（含模型接入半层，以及贯穿全层的**模态轴**与**时程轴**两条横切维度）、约五十五张 GoF 风格设计模式卡、二十个可运行的关键 demo，和一整套可复用的决策工具（选型矩阵、ADR 模板、上线检查清单）。读完这本书，你交付的不只是代码，还有能让 CEO 和团队信服的架构决策记录。

与前作的关系：《数字见习生》回答"AI agent 是什么、普通人怎么用"；本书回答"agent 系统怎么设计、技术负责人怎么决策"。两书独立成篇，可在前言/封底互相引荐，形成"使用者入门＋构建者深潜"双书矩阵。

## 二、时机判断（为什么是现在写）

1. **技术面从炒作期进入收敛期，第一次有了"值得写进书里"的稳定对象。** 协议层是最强信号：MCP 以约 9700 万下载量赢下 agent-工具层，Anthropic/OpenAI/Google/Microsoft 全部采纳，已入 Linux Foundation；A2A 进入 Linux Foundation 一年后（2026-04）汇聚 150+ 组织、落地主要云平台并进入企业生产（来源见§十三，下同）。2026 被业界称为"协议收敛之年"——收敛意味着可以写"格局与边界"，而不只是追逐新闻。
2. **模型层仍在剧烈变化，恰恰需要一本讲"不变量"的书。** 框架年年换、模型季季换，但循环本质、上下文经济学、分布式系统类比、安全原理这些 L1 层知识的半衰期在五年以上。本书的时效分层策略（§九）正面解决这个问题。
3. **中文出版空窗。** 中文世界目前唯一的系统性同类作品是免费在线书（绑定作者自家开源项目，非出版物）；Gulli 的《Agentic Design Patterns》中译本走百科式动手路线且非决策导向。**"中文纸质 × 架构师决策视角"这个位置现在没人占。**
4. **读者基数已成型。** 2024-2026 三年间大量后端/平台工程师被推上 agent 项目，其中先进者正在晋升为"agent 架构决策者"——他们买书不是为了入门，是为了做对决策、说服别人。
5. **两个维度在 2026 年恰好从"功能特性"变成了"架构问题"。**
   - **多模态**：模型的模态支持已经矩阵化（图像/文档/音频/视频/屏幕），生产瓶颈随之从"模型能不能看"转移到"感知管线怎么切、模态上下文怎么计价、多模态注入怎么防、跨模态记忆怎么存"。computer use 是这条线最尖锐的例子——基准分数逐年走高，但真实长程工作流的成功率仍显著低于基准，且"截图-思考-行动"循环对动态界面存在结构性限制（OSWorld 2.0，2026-06）。这种"能力有余、可靠性不足"的落差，正是需要架构判断而非功能罗列的时刻。
   - **多模型**：供应商限流与宕机、成本压力、数据驻留合规、开源权重小模型成熟，四股力量叠加，使"模型池＋网关＋路由"在 2026 年成为默认基础设施形态（AI 网关产品同年集中成熟并被企业采购目录收录）。架构师必须为它做治理决策——谁批准接入新模型、能力画像谁维护、降级到什么、退出成本多少——而不是让每个服务各自硬编码一个模型。
6. **第三个维度同年浮现：agent 的时间尺度被拉长了一个数量级（v0.2 新增判断）。** 2024 年的 agent 活在一次对话里，2026 年的 agent 要活过小时、天乃至周——deep research、后台 agent、跨天迁移核查一类任务进入生产。持久执行（durable execution）从工作流引擎的专利变成 agent 运行时标配（Temporal 一系、Azure Durable Task for AI Agents、Google ADK 的 pause/resume 均在 2026 年成型）。但**长时程不是"更长的循环"**：单步 90% 可靠的动作串 50 步，端到端成功率只剩约 0.5%——误差复利决定了它必须被重新设计（可续跑分解、外部验证、放弃判据、上下文重建、进度契约）。研究显示长时程失败以过程级失败为主（约七成发生在顺序推进过程中的环境交互环节），这类失败靠"换个更强模型"解决不了，只能靠架构解决。
   - **三个维度的共同点**：它们都不是"再加一章新技术"，而是要改写参考架构本身。所以本书把多模态做成**模态轴**、把长时程做成**时程轴**（两条横切 L1-L5 的维度），把多模型做成 **L1b 接入半层**——而不是像竞品那样塞进"前沿实践"散章。这正是本书的差异化。

## 三、目标读者

### 画像 P1：平台架构师 / 技术总监（首要读者，全书为 TA 而写）
- 35±5 岁，管 5-20 人团队，公司正要上 agent 项目或已有雏形失控
- 痛点：要决定自研还是用框架、单 agent 还是多 agent、要不要接 MCP、**用几个模型和要不要建网关、要不要上多模态、哪些任务该后台化**；要给 CEO 写方案、给团队定规范；网上资料碎片化且互相矛盾
- 从本书获得：参考架构、模式目录、决策框架、ADR 模板——**能直接带去开架构评审会的东西**

### 画像 P2：资深工程师转型 AI 工程（次要读者）
- 会写代码、懂分布式，缺 agent 领域的系统地图
- 从本书获得：从循环本质到生产治理的完整知识骨架，demo 代码可上手复现

### 画像 P3：技术顾问 / 解决方案架构师（次要读者）
- 为客户做 agent 方案设计与评审
- 从本书获得：选型维度、风险清单、反模式目录——评审别人的方案时最好用

### 非目标读者（书里明说，避免错配差评）
- 零编程基础读者 → 请读《数字见习生》
- 只想 30 分钟跑通一个 demo 的尝鲜者 → 框架官方 quickstart 更快
- 前沿研究者 → 本书引用论文但不做学术综述
- **想学多模态模型本身（训练/微调 VLM、语音模型）的读者 → 本书只讲多模态的系统架构，不讲模型内部**

### 前置要求
- 熟练的编程经验（任何语言）；了解 HTTP/JSON/数据库等工程常识
- LLM 使用经验（调过任一聊天 API 即可）；**不要求**了解任何 agent 框架，**不要求**了解多模态模型，**不要求**用过工作流引擎（第16章会从零讲清持久执行的本质）

### 本书差异化五支柱
1. **决策科学视角**：每章以真实决策场景开场、以决策指引收尾（何时用/何时不用/风险清单/权衡表）；贯穿案例"智航科技"（§六）让 20 章的决策连成一家公司的完整旅程。
2. **模式卡片目录**：GoF 风格的约 55 张模式卡（意图/结构/适用/不适用/风险/关联模式/实例），附录 A 总成速查目录——中文纸质书里独一份。
3. **时效分层机制**：内容按半衰期分 L1/L2/L3 三层并显式标注，L3 事实全部带"截至 2026-10"锚点＋配套页面承接更新（§九）。这是《数字见习生》时效体检经验的升级版，也是所有竞品都没做的。
4. **纸书级图表体系**：一张五层参考架构总图贯穿全书，每章放大一块；模式结构图＋时序图约 80 幅，Mermaid/SVG 精确制图（非 AI 插画），印刷质量可控。
5. **三个新维度的架构化归位（v0.1-v0.2 形成）**：把"多模态"讲成横切的**模态轴**（它同时改写 L1 的能力探测、L2 的上下文预算、L3 的感知管线、L5 的评估与安全），把"长时程"讲成横切的**时程轴**（它同时改写 L2 的上下文重建、L4 的持久执行、L5 的跨天预算与进度契约），把"多模型"讲成 **L1b 接入半层**的治理问题（能力画像、网关、路由分层、降级矩阵、退出成本、合规驻留）。竞品把这三件事放在"前沿实践"或"成本优化"里，本书把它们放进参考架构——因为架构师真正要拍板的是后者。

## 六、内容主线与结构逻辑

### 三部结构：认知 → 模式 → 决策

```
第一部 认知与基础（第1-4章）    建立共同语言：agent 是什么、系统长什么样、
                              模型层（单个模型的能力 ＋ 一群模型的接入）如何制约架构
第二部 设计模式深潜（第5-14章）  九个模式族、共十章，全书主体：规划/上下文/工具/记忆/
                              反思/编排/多智能体/协议/多模态（因体量拆为上下两章）
第三部 生产与决策（第15-20章）   架构师的职场：运行时、长时程与后台化、安全、评估、
                              成本、选型与组织落地
附录 A-E                        模式速查目录、术语表、决策工具箱、时效说明、延伸阅读
```

结构逻辑对应架构师的真实工作流：**先看懂系统（认知）→ 再掌握机制（模式）→ 最后做出决策并为之负责（生产与决策）**。第二部按"五层参考架构"逐层放大，第三部把治理层与横切决策收拢。

**v0.1→v0.2 的三处结构变化及其理由（均源自作者第二批拍板）：**
- **多模态拆为上下两章（第13、14章）**：一章 12k 装不下"感知与文档"＋"语音、屏幕与输出"两组差异极大的内容——前者是**批处理式**的（准确率、token 计价、管线选型），后者是**实时式**的（延迟预算、事件驱动、打断与轮次）。两者的决策场景、评估指标、失效模式都不同，硬塞一章会让读者拿不到可操作的判定。拆开后上章 10k／下章 9k，仍属同一"多模态"模式族（7 张卡分置两章）。
- **长时程与后台任务独立成章（第16章），置于第三部运行时章之后**：它消费第15章的执行底座（状态外置、持久化介质），又向第17章（无人值守权限）、第18章（长任务怎么评）、第19章（跨天预算）供血。放第三部而非第二部，因为它的主要内容是运行时、可观测与治理，不是循环内的控制流模式；但它确实贡献 4 张新模式卡，故在附录 A 中独立成族。
- **总图增列时程轴**：与模态轴对称——模态是空间维度的横切，时程是时间维度的横切。两条轴加 L1b 半层，构成 v0.2 参考架构相对业界通行画法的全部增量，书中会如实声明这是本书的建模而非标准。

### 贯穿案例："智航科技"（虚构，B2B 客服/工单 SaaS 厂商，约 200 人）
每章开篇的决策场景与章末的"架构师视角"回应当都取自同一家公司的 agent 化七阶段旅程：

```
客服副驾与     自主工单    平台化·多agent   多模态      执行底座与    生产事故    年度架构
模型接入整顿 →  agent   →    ·协议     →    扩展   →   长时程化  →   与治理  →    评审
 （第1-4章）  （第5-9章）  （第10-12章） （第13-14章） （第15-16章）（第17-19章）（第20章）
```

案例中承接三个新维度的具体情节（均为虚构）：
- **模型接入**（第4章）：三套 agent 各自硬编码了一个供应商，某次上游限流导致全线停摆，同时 CFO 质问"为什么一个分类任务也在用旗舰模型"。
- **多模态**（第13-14章）：客户开始上传报错截图、合同扫描件与呼叫中心录音，只会读文本的工单 agent 哑火；安全团队同时提出"图片里也可能藏指令"；随后运维团队希望 agent"自己点后台管理界面"处理没有 API 的遗留系统，客服部门则要求接入实时语音坐席辅助。

#### 第4章 模型接入层：模型池、网关与能力路由
- 4.1 决策场景：智航的三套 agent 各自硬编码了一个供应商；一次上游限流让全线停摆，CFO 同时质问"为什么一个分类任务也在用旗舰模型"
- 4.2 从"一个模型"到"模型池"：为什么生产系统的默认形态是模型组合——四股驱动力（能力异构、成本异构、供应商风险、合规与驻留分区）；L1b 半层的由来
- 4.3 **能力画像（capability profile）**：把模型当"有规格的组件"管理——上下文窗口/工具调用格式与并行调用支持/结构化输出可靠性/**模态输入输出（一等字段，回指 3.5、供第14章模态驱动路由使用）**/推理模式与思维链预算/延迟与吞吐/单价（含缓存价）/许可与数据驻留/弃用周期。画像既是路由的输入，也是选型的输出，还是回归测试的基线
- 4.4 **模型网关（gateway）架构**：单一入口、供应商 API 归一化、**模型快照固定（snapshot pinning）**、租户配额与预算、密钥托管、集中策略、按路由遥测——网关 vs 应用内薄适配层（`llm.py`）的分工与演进路径（什么时候适配层就够、什么时候必须上网关）
- 4.5 **路由的四类策略与分层组合**：规则路由（可调试、覆盖窄）／语义（嵌入）路由（覆盖长尾、需阈值与漂移监控）／预测（分类器）路由（精度最高、需大量标注与延迟税）／级联（生成后）路由（绕开"预测难度"这个最难的问题，代价是升级请求双跑）。生产系统的收敛形态是**分层叠加**而不是单选；并给出"什么时候才配得上学习式路由"的数据门槛
- 4.6 **路由的三个目标、三种度量**：韧性路由（成功率/故障期间可用性）、成本路由（单位任务成本，且必须含重试与级联双跑）、质量路由（评估驱动，需评估层垫底，呼应第18章）——目标混淆是最常见的路由失败根因
- 4.7 **Agent 场景的路由特殊性**：一次用户回合 = 多次模型调用（规划/工具选择/摘要/生成/判官），**每个调用点独立路由**；只优化第一跳约等于只优化两成开销；调用点级路由表的设计与治理
- 4.8 **故障转移与降级**：熔断阈值与退避、幂等重放、跨供应商降级的真实代价（换模型＝换工具调用格式、换系统提示行为、换缓存命中，**降级不是改个模型名**）；降级矩阵的写法
- 4.9 **供应商锁定与退出成本**：抽象层能抽象掉什么、抽象不掉什么（提示词与模型的行为耦合、工具调用风格、结构化输出行为、思维链预算、缓存前缀）；退出成本的量化方法与"可移植性预算"
- 4.10 **合规与数据驻留路由**：受监管数据走本地/私有部署模型的策略位置（应在网关策略层第一天写入，而非事后补）；开源权重与小模型（SLM）的能力-成本-主权三角【L3 锚点】
- 4.11 **模型弃用与代际更替的运行手册**：版本快照、影子评估（shadow eval）、灰度切换、回滚门槛——把"换模型"从项目变成一次普通变更（与 3.6 呼应，此处给流程；门禁落地见 18.5）
- 4.12 路由的反模式：没有生产日志就上学习式路由、只看单价不看总成本、缓存放在路由之后、路由逻辑散落在各服务、把熔断当重试、为"未来可能的多模型"提前建网关
- 模式卡：**能力画像路由／语义路由／级联升级／模型网关／故障转移与熔断**（5 张，"模型编排与路由"模式族）

### 第二部 设计模式深潜（九个模式族，共十章）

#### 第13章 多模态架构（上）：感知、文档与模态预算

- 13.2 **模态是横切维度，不是一层**：多模态在 L1a（模型原生支持哪些模态、支持到什么可靠性）／L2（非文本信息在上下文里怎么表示、占多少预算）／L3（感知管线）／L5（多模态评估与注入防御）上各自的含义——模态轴总图导读（与第14章共用）

- 13.4 **模态归一化与中间表示**：把图像/文档转成"语言模型能可靠消费的东西"——文本化、结构化 JSON、切片与标注；**中间表示即架构契约**（可单测、可缓存、可回放、可脱敏），以及"过早文本化丢失了什么"的清单（版式、颜色语义、空间关系、置信度）
- 13.5 **视觉即工具（vision-as-tool）**：不给主模型装眼睛，而是给它一个"看"的工具（截图→描述/OCR/元素定位/坐标返回）；与原生 VLM 的分工判据；上下文预算、可复用性、可降级性三笔账（承接 7.3 工具粒度、7.7 感知类工具）

#### 第14章 多模态架构（下）：语音、屏幕与输出模态
- 14.1 决策场景：智航客服部门要接呼叫中心录音与实时语音坐席辅助；运维团队同时希望 agent"自己点后台管理界面"去操作没有 API 的遗留系统——两个需求都被估成"加个多模态模型"，实际是两个不同的架构问题
- 14.2 **实时性是一条新的架构约束**：延迟预算从"秒级可接受"变成"数百毫秒级"，它把请求-响应式编排换成事件驱动式编排；上章的批处理式多模态与本章的实时式多模态在评估指标、失效模式、成本结构上的根本差异
- 14.3 **语音与实时交互架构**：事件驱动管线（ASR/LLM/TTS 与感知处理器并发流）、**传输层定义能力上限**（WebRTC、帧率与抖动缓冲）、轮次检测与打断（turn-taking/barge-in）、端到端延迟预算分解与各段配额（承接 10.4 状态机编排）
- 14.4 **语音 agent 的评估与运维差异**：为什么文本 agent 的评估集不能直接复用（打断、静默、误触发、口语纠错、方言与噪声）；实时链路的可观测性必须按段计延迟（ASR/推理/首字节 TTS/端到端）；录音数据的合规位（回指 13.8）
- 14.5 **屏幕-动作循环（computer use / GUI agent）**：循环结构、可靠性现状（基准分数与真实长程工作流成功率的落差）、"截图-思考-行动"循环面对动态界面的结构性限制；**判定：什么时候用 computer use、什么时候改造出 API、什么时候用专用工具**【L3 锚点】（与 16.3 误差复利同框：屏幕动作的单步可靠性最低，链路最长）
- 14.6 **屏幕模态的执行底座要求**（与第15章分工：本章讲架构与判定，15.5 讲隔离、会话录制审计与急停）
- 14.7 **输出模态**：TTS、图像与图表生成、文档产出进入 agent 循环——生成物的校验方式、工件（artifact）管理与版本、版权与合规位、"输出模态也是攻击面"（呼应 11.5 工件传递）
- 14.8 **视频与流式模态**：采样策略与帧预算、"看不过来"的处理（关键帧提取、事件触发、降采样）、流式模态与实时链路的合流【L3 锚点】
- 14.9 **多模态与模型池的交汇**：不是所有模型都支持所有模态，模态是能力画像的一等字段（回指 4.3）；**模态驱动的路由**（有图走 VLM、纯文本走小模型、实时语音走低延迟供应商）与模态降级的代价
- 14.10 反模式：以为换个多模态模型就解决了管线问题、把原始媒体全量塞进上下文、用 computer use 替代本该建的 API、实时链路不留分段延迟观测、输出模态不做校验、用文本评估集验收语音 agent

- Demo D-17：屏幕-动作循环最小实现——**用录制的截图序列回放**（全离线、不驱动真实桌面），观测三类失效点（元素定位漂移、动态界面、误点不可逆操作）

#### 第16章 长时程 Agent 与后台任务：时间维度上的架构
- 16.1 决策场景：智航接下"跨三天的客户系统迁移核查"，工单 agent 跑到第四小时服务重启、进度全丢，客户追问"到底做到哪了"；复盘还发现预算在无人值守的夜里悄悄烧穿
- 16.2 **时程轴**：秒级对话 → 分钟级任务 → 小时级流程 → 天级后台任务；为什么时程是横切维度（它同时改写 L2 的上下文重建、L4 的持久执行、L5 的跨天预算与进度契约），与模态轴对称；**四档时程各自的架构基线**（一张对照表，是本章最常被复印的一页）
- 16.3 **误差复利：长时程不是"更长的循环"**：端到端可靠性 ≈ 单步可靠性^步数（单步 90% 的动作串 50 步只剩约 0.5%）——这条算式决定了长时程必须被重新设计；三个对冲方向：**缩短链路**（分解与合并动作）、**提高单步可靠性**（外部验证器而非模型自评，回指 9.4）、**插入检查点**（让失败可回退而非从头再来）；过程级失败为主的实证结论【L3 锚点】
- 16.4 **可续跑分解**：把长任务切成"可独立验证、可重放、幂等"的单元；单元粒度的判据（重跑成本 vs 检查点开销 vs 上下文占用）；与第5章规划模式的关系——**跨小时/跨天的任务里显式计划重新变成必需品**（隐式规划撑不过一次上下文重建）
- 16.5 **检查点与持久执行**：状态外置（工作区文件/数据库/工作流引擎）、事件溯源式重放、Temporal 与 durable task 一系范式的本质（承接 10.5 的循环内视角，落到基础设施见 15.6）；**三种恢复语义的差别**：崩溃恢复（同进程内）、断电续跑（跨进程）、跨天恢复（跨上下文窗口）——它们的正确性要求完全不同；**幂等性是重放的硬前提**（回指 7.5）
- 16.6 **恢复后的上下文重建（rehydration）**：跨天后原上下文早已不在窗口里——重建什么（目标、已完成、待办、约束、失败教训、外部状态）、用什么重建（交接文档、工作区文件、任务级记忆）、**重建的验证（"恢复即测试"：恢复后先跑一遍自检再干活）**；与 6.4 交接文档模式、6.7 文件即外存、8.x 记忆的同源关系；任务级记忆 vs 跨任务记忆的边界
- 16.7 **进度可见性与用户信任**：进度事件流的设计（里程碑事件 vs 心跳 vs 增量产物）；**"沉默的 agent"为什么不可接受**（无法区分"在干活"与"卡死了"）；部分结果交付；可中断与可接管（HITL 在长时程里从可选变必需，回指 10.6）
- 16.8 **放弃、超时与预算**：超时策略的三层（步骤级/任务级/预算级）；**放弃判据**（无进展检测、重复动作检测、置信度衰减、外部条件失效）；跨天预算累积与熔断（回指 4.6 三目标与 19.7 预算护栏）；**失败后的可交付物**——"失败了也要交出中间成果与失败原因"是长时程任务的验收底线
- 16.9 **后台化与调度**：从"用户等着"到"任务排队"——队列、并发上限、优先级、租户公平（底座见 15.7）；**无人值守时的权限收敛**（交互式权限不能带进后台，回指 17.4 最小权限）与护栏加严；后台任务的触发方式（定时/事件/人工）与重入控制
- 16.10 **长时程的可观测与评估**：怎么评一个跑三天的任务（分段评估＋里程碑门禁＋人工抽检，而不是只看端到端成功率）；追踪的时间尺度问题（span 跨天如何组织）；失败归因的口径（过程级 vs 结果级）；成本归因跨天累积（回指 18.6）【L3 锚点】
- 16.11 长时程的反模式：把长任务塞进一个上下文窗口、无进展检测的死循环烧钱、**检查点存了但恢复从没演练过**、进度只有日志没有事件契约、无人值守仍用交互式权限、失败即全丢（不交中间成果）、用"更强模型"解决复利问题
- 模式卡：**可续跑分解／断点续跑（检查点与持久执行）／恢复后上下文重建／进度事件流**（4 张，"长时程"模式族；放弃与超时策略并入"预算护栏"共卡，见第19章）
- Demo D-18：后台长时程任务——**进度事件流＋预算熔断＋被 kill 后从检查点恢复并重建上下文**（与 D-11 的编排器基座对接：D-11 演示机制，本 demo 演示治理；用一个压缩到几分钟的"模拟三天任务"跑完全流程，支持 `--mock`）

- 时效注意：持久执行产品与后台 agent 平台格局（Temporal 一系、Azure Durable Task for AI Agents、Google ADK 的 pause/resume、各家 background agent 能力）为 L3，集中收纳在 16.5 与 16.9 末尾并打锚点；16.2-16.4、16.6-16.8、16.11 为 L1

## 八、写作风格与体例规范

### 章节骨架（八段式，全书统一）
1. **决策场景**（智航案例，300-500 字）——问题先行
2. **本章地图**（一段话＋小节导航）
3. **原理深潜**（主体，机制讲到 token/消息/状态级别，但用架构师语言）
4. **模式卡**（穿插或集中于章中，格式见下）
5. **架构图**（每章 3-8 幅）
6. **关键 demo**（如有：讲解＋核心代码＋"观察什么"）
7. **决策指引**（何时用/何时不用/风险清单/权衡表——本章的可带走资产）
8. **架构师视角盒**（1-2 个）＋小结＋延伸阅读（3-5 条带一句话评注）

### 模式卡格式（九字段，全书约 55 张）
名称（中英）｜意图（一句话）｜问题（什么困境下出现）｜结构（小图）｜适用场景｜**不适用场景**（竞品普遍缺失的字段）｜风险与代价｜关联模式｜出处与实例（论文/开源系统/智航案例，带年份）

### 语言与术语
- 中文为主，术语首次出现给中英对照（如"上下文压缩（compaction）""能力画像（capability profile）""模态归一化（modality normalization）""上下文重建（rehydration）"），此后中文为主；附录 B 统一
- 语气：资深架构师对同行讲话——直接、有观点、敢下判断；判断必须给理由和边界
- 有观点但不站队：对争议（如多 agent 论战、原生多模态 vs 感知管线、自建 vs 持久执行引擎）呈现双方最强论点后给本书判定
- 禁用营销话术（"革命性""颠覆"）；数字必须带来源与日期
- **同名不同物必须显式辨析**：如"路由"在工作流编排与模型选择两个语境下含义不同、"检查点"在编排器与持久执行引擎里语义不同、"恢复"有三种（崩溃/断电/跨天），首次共现处必须辨析并在附录 B 立条
- **算式必须可复算（v0.2 新增）**：凡用于论证的算式（如误差复利 0.9⁵⁰≈0.5%）须在正文给出完整计算过程与前提假设，不得只给结论

### 代码规范（混合策略的具体化）
- 全书 20 个关键 demo（§十），每个 ≤150 行核心代码，书中展示骨干片段＋完整代码入配套仓库
- 正文以架构图、时序图、伪代码为主；伪代码语言中立
- 所有代码不绑定商业框架（直调模型 API），模型通过薄适配层可替换
- 代码块标注语言与"该片段在 demo 仓库中的文件路径"
- **多模态、路由与长时程类 demo 的额外约定**：必须提供 `--mock` 离线模式（无网络、无 API key 也能跑通全流程，用录制回放或本地替身），否则读者无法复现、编辑也无法审校；**长时程 demo 必须把"三天"压缩到几分钟内可跑完（模拟时钟），不得要求读者真的等**

### 图表规范
- 三类图：总图放大系（源自第2章五层两轴总图，含 L1a/L1b、模态轴、时程轴四个放大方向）、模式结构图（UML 风格）、时序/流程图
- 工具链：Mermaid 源稿（入库、可 diff、可再生）→ SVG 导出 → docx 嵌入；印刷前统一风格审查
- 概念性章首图可用 AI 插画（复用《数字见习生》插画管线经验），技术图一律精确制图
- 图编号按章（图 4-1），表同（表 4-1）；每图必有图题与一句话导读
- 多模态章的图像素材须遵守 13 章"素材纪律"，且印刷为黑白时需自检可辨识（不依赖颜色区分模态）
- **误差复利一类曲线图须标注坐标轴单位与假设前提，避免被误读为实测数据（v0.2 新增）**

### 事实纪律（沿用并升级《数字见习生》纪律）
- 占位事实用【方括号】，读者填写位用下划线（本书预计极少）
- 外部数据三要素：数字＋来源＋日期；来源集中在附录 E 与各章延伸阅读
- 虚构声明：智航科技案例首次出现处声明虚构；任何与真实公司的相似为巧合
- 多模态素材的来源与授权链须留档台账（自制/授权/公有领域三选一，禁止来历不明截图）
- **第三方基准分数与"成功率"类数字必须标注基准名称、版本与测量条件，禁止裸引（v0.2 新增，因长时程与 computer use 两处的基准最容易被误用）**

## 九、时效策略：内容半衰期分层（本书的核心工程创新）

agent 领域的时效衰减比《数字见习生》面对的快一个数量级，故把时效治理从"机制补丁"升级为"内容架构"：

| 层 | 内容 | 半衰期 | 占比目标 | 处理方式 |
| --- | --- | --- | --- | --- |
| **L1 原理层** | 循环本质、上下文经济学、安全原理、分布式类比、路由与降级的策略学、感知-推理分离与中间表示契约、**误差复利与可续跑分解**、决策方法论 | 5 年＋ | ~62% | 全书主体，正常写作 |
| **L2 模式层** | 设计模式、架构风格、拓扑、评估方法、网关与路由的分层组合形态、多模态管线架构、**检查点与上下文重建模式** | 2-5 年 | ~28% | 模式卡出处栏记录提出年份，便于读者判断演化 |
| **L3 事实层** | 协议版本与采纳数字、框架格局、网关与路由产品格局、模型能力现状、模态支持矩阵与计价方式、computer use 与多模态基准分数、**持久执行与后台 agent 平台格局**、法规 | 6-18 个月 | ~10% | **集中收纳**（每章独立小节，不散落正文）＋显式锚点 |

- L3 锚点标记语法：`【时效锚点｜截至 2026-10】`，正文可见（读者知道哪些内容会过期、过期去哪查）
- 附录 D 汇总全书 L3 锚点成表——读者半年后重读时可逐项核对
- 配套页面承诺：附录 D 给出配套页面信息块（复用《数字见习生》C-4 信息块体例），承诺 L3 层的季度更新；托管方待定（外部依赖）
- 写作纪律：任何论断若依赖 L3 事实，必须同时给出"L3 失效后论断如何降级"的写法（例："MCP 是当前工具层事实标准【锚点】；即便未来出现替代协议，本章的防腐层模式依然成立"／"当前视觉文档检索尚不成熟【锚点】；即便它成为主流，13.4 的中间表示契约依然是设计要点"／"今日后台 agent 平台能力差异很大【锚点】；但 16.3 的误差复利与 16.8 的放弃判据不依赖任何平台"）
- 占比说明：三个新维度的 L3 密度高于全书均值（产品格局、模态矩阵、基准分数、平台能力都是快速变动项），故 L3 目标占比由 v0 的 7% 上调至 10%、L1 由 65% 下调至 62%；新章的 L3 内容严格执行"集中收纳"，不得渗入原理小节。prepub 规则须校验这几章的锚点密度与收纳位置。

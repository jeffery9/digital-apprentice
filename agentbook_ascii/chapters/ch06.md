# 第6章 多智能体协作与评估

## 6.1 什么时候需要多个 Agent

单 Agent 上下文膨胀、职责混杂时，可拆分为专职子 Agent。常见编排模式：

- **主管-下属（Orchestrator-Workers）**：主管分解任务并分派，下属并行执行，结果汇总。
- **流水线（Pipeline）**：采集 → 清洗 → 分析 → 撰写，各节点单一职责。
- **辩论/评审（Debate & Critique）**：生成者 + 批评者对抗提升质量。
- **群聊（Group Chat）**：共享消息总线，由路由器决定下一个发言者。

拆分的前提是收益大于成本：每多一个 Agent，就多一份延迟、Token 开销与调试复杂度。

## 6.2 通信与状态一致性

多 Agent 系统必须回答三个工程问题：

1. **消息语义**：用结构化消息（任务卡）而非自由文本传递子任务，字段含目标、约束、验收标准。
2. **共享状态**：以"黑板（工作区文件/数据库）"为唯一事实源，避免两个 Agent 各自维护副本。
3. **失败传播**：子任务失败要能回溯到主管触发重规划，而不是静默吞掉。

## 6.3 评估体系

Agent 评估比模型评估更复杂，因为存在随机性、长链条与外部副作用。推荐三层指标，图 6-1 给出了评估仪表盘示意。

![图6-1 Agent 评估：成功率、效率与安全指标](figures/fig6_eval.png)

| 层级 | 指标 | 说明 |
| --- | --- | --- |
| 结果层 | 任务成功率、答案质量分 | 端到端，最重要 |
| 过程层 | 步数、工具调用准确率、重试率 | 定位能力短板 |
| 成本层 | Token 消耗、时延、单次任务费用 | 决定能否规模化 |

实践建议：

- 构建**黄金测试集**（50~200 个真实任务），每次改动跑回归。
- 用 **LLM-as-Judge** 打过程分，但抽样人工校准评判器偏差。
- 记录完整轨迹回放（Trace Replay），失败案例是最宝贵的改进素材。

## 6.4 安全与对齐要点

- 防**提示注入**：把检索到的外部内容一律视为数据而非指令。
- 权限分级：只读操作自动放行，写操作按风险等级审批。
- 预算护栏：对每个任务设置 Token/金钱/步数上限，超限熔断。

## 6.5 本章小结

多 Agent 是架构手段而非目的；评估与安全则是把 Demo 变成产品的分水岭。能用单 Agent + 好工具解决的，就不要急着上多 Agent。
